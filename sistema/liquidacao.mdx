## O que é liquidação

Liquidação é o processo pelo qual o dinheiro de um pagamento se torna **disponível para saque** pelo organizador. Dependendo do método de pagamento, pode ser imediata ou passar por um período de hold.

## Status de liquidação (`clearanceStatus`)

| Status | Descrição |
|--------|-----------|
| `NOT_APPLICABLE` | Sem pagamento (inscrições cortesia) |
| `IMMEDIATE` | Liquidado imediatamente (PIX) |
| `PENDING` | Em período de hold (cartão, aguardando liquidação) |
| `CLEARED` | Hold encerrado, valor disponível para saque (cartão após hold) |

---

## PIX — Liquidação Imediata

Pagamentos via PIX têm liquidação **instantânea**. Assim que o webhook de confirmação é recebido:

- Status da inscrição: `PAID`
- `clearanceStatus`: `IMMEDIATE`
- O valor líquido é somado **imediatamente** ao `totalNetReceived` do evento
- O organizador pode solicitar saque no mesmo instante

---

## Cartão — Período de Hold

Pagamentos via cartão passam por um período de hold antes de ficarem disponíveis. Isso ocorre porque a operadora pode fazer estorno (chargeback) dentro de um prazo.

O tempo de hold é configurado por evento no campo `settlementHoldDays` do `PaymentMethodConfig`. O **padrão** é **32 dias** (variável `ASAAS_DEFAULT_SETTLEMENT_HOLD_DAYS`).

### Fluxo do cartão com hold

```
Pagamento confirmado (webhook)
        ↓
clearanceStatus = PENDING
Valor somado a: totalPendingClearance
availableAt = dataConfirmação + settlementHoldDays
        ↓
Cron job diário verifica: availableAt ≤ agora?
        ↓
Sim → clearanceStatus = CLEARED
      Valor movido: totalPendingClearance → totalNetReceived
      Organizador pode sacar
```

### Cron job de liquidação

Uma tarefa agendada roda diariamente e processa todos os pagamentos de cartão com `clearanceStatus = PENDING` cujo `availableAt` já passou. Para cada um:

1. Atualiza `clearanceStatus` para `CLEARED`
2. Decrementa `totalPendingClearance` pelo valor líquido
3. Incrementa `totalNetReceived` pelo mesmo valor

<Info>
O cron utiliza **lock distribuído** para garantir execução única mesmo em deployments multi-instância. Se uma instância já estiver processando o lote, as demais aguardam sem processar em paralelo — eliminando risco de duplo crédito.
</Info>

## Conta financeira do evento (EventAccount)

Cada evento tem uma conta financeira com os seguintes campos:

| Campo | Descrição | Visível para |
|-------|-----------|-------------|
| `totalReceived` | Soma bruta de todos os pagamentos confirmados | Organizador e Admin |
| `totalPendingClearance` | Valor de cartão ainda em período de hold | Organizador ("Aguardando liquidação") e Admin |
| `totalNetReceived` | Valor já liquidado e disponível (PIX imediato + cartão após hold) | Organizador e Admin |
| `totalWithdrawn` | Total já sacado pelo organizador | Organizador e Admin |
| `totalNetAvailable` | Saldo disponível para novo saque (`totalNetReceived − totalWithdrawn`) | Organizador e Admin |

### Saldo disponível para saque

```
saldo disponível = totalNetReceived − totalWithdrawn
```

### Cálculo do líquido creditado

Ao confirmar um pagamento, o sistema calcula o valor que vai ao organizador (ou ao saldo pendente para cartão):

```
líquido creditado = amount − moneyRate − gatewayFeeAmount
```

- `amount` — valor total cobrado do atleta
- `moneyRate` — snapshot da taxa operacional da plataforma (custo por inscrição)
- `gatewayFeeAmount` — taxa cobrada pelo gateway de pagamento, calculada pelo FeeEngine no momento da inscrição

O mesmo cálculo é usado em `buildWithdrawalPaymentAllocations` ao validar o saldo disponível para saque.

## Resumo por método de pagamento

| Método | Hold | Liquidação | Campo inicial |
|--------|------|-----------|---------------|
| PIX | 0 dias | Imediata no webhook | `totalNetReceived` |
| Cartão | `settlementHoldDays` (padrão: 32 dias) | Cron diário após hold | `totalPendingClearance` → depois `totalNetReceived` |
| Cortesia (FREE) | — | Não aplicável | Nenhum campo financeiro alterado |

## Cartão parcelado — liquidação em bloco (não por parcela)

No parcelamento, o banco confirma mensalmente cada parcela ao longo de N meses. Porém, do ponto de vista da liquidação, o sistema credita o valor **uma única vez** — na confirmação da primeira parcela — e rastreia as confirmações seguintes apenas para auditoria.

### Por que em bloco?

O campo `amount` do registro `Payment` representa o **valor total do parcelamento** (ex.: 5× R$100 = R$500). Quando o gateway confirma a parcela 1, o backend credita o líquido total esperado em `totalPendingClearance` e define `availableAt`. As parcelas 2–N apenas incrementam `paidInstallments` e acumulam `actualNetCents` para conciliação — sem alterar `totalPendingClearance` novamente.

```
Parcela 1 confirmada  → totalPendingClearance += líquido total esperado (net)
                         availableAt = dataConfirmação + settlementHoldDays
                         clearanceStatus = PENDING

Parcelas 2, 3 … N    → paidInstallments += 1            (auditoria)
                         actualNetCents  += líquido desta parcela  (conciliação)
                         (totalPendingClearance: sem alteração)

Cron diário (quando availableAt ≤ agora):
  clearanceStatus = CLEARED
  totalPendingClearance -= líquido total
  totalNetReceived      += líquido total
  → Organizador pode sacar
```

O hold de 32 dias cobre toda a janela de parcelamento típico, garantindo que eventuais chargebacks sejam absorvidos antes de o valor ficar disponível para saque.

<Warning>
**O organizador não saca por parcela.** O saque ocorre quando o período de hold encerrar (após `availableAt`), liberando o valor total de uma só vez. `paidInstallments` e `actualNetCents` são campos de auditoria — não alteram o saldo disponível individualmente.
</Warning>

<Info>
Use `paidInstallments` / `totalInstallments` para saber quantas parcelas o banco já confirmou. O `installmentGroupId` permite filtrar todas as confirmações de um mesmo parcelamento para auditoria detalhada. Para detalhes sobre correção de `totalInstallments` quando o atleta muda a parcela no checkout, veja [Fluxo de Pagamento](/sistema/fluxo-pagamento#correção-de-totalinstallments).
</Info>

## Reembolsos e impacto na liquidação

Quando uma inscrição é reembolsada:

- O gateway estorna o valor ao atleta
- O `totalNetReceived` é reduzido pelo valor líquido da inscrição
- Se o valor já foi sacado, o organizador fica com saldo negativo até compensar

Reembolsos são sempre coordenados com o administrador da plataforma.
